# 00. 开发主指导（必读）

本文件只约束“怎么开发不会把项目越改越乱”。所有说明都以当前代码结构为准。

## 1. 开发前必须先做

1. 先读 `docs/开发文档/README.md`
   - 先判断需求属于哪个模块。
2. 再读 1 份对应模块文档
   - 地图 / 月结算：`02-地图生成与月度结算模块.md`
   - 节点 / 布告栏 / 仪式：`03-节点交互模块.md`
   - 英雄 / 队伍 / 装备 / 技能 / 记忆：`04-英雄与队伍模块.md`
   - 状态 / 类型 / 数据边界：`05-状态管理与数据模块.md`
   - 样式：`06-UI与样式模块.md`
   - 战斗：`07-战斗系统模块.md`
   - 调参数：`配置文件修改指南.md`
3. 至少确认 3 个入口
   - 页面入口
   - 对应 Provider / lib
   - 对应 data / config
4. 项目基础设定：放置类游戏

## 2. 开发约束

### 2.1 先确认“状态归谁管”，不要新增平行状态源

1. 地图、地区、任务、世界月份、世界日志归 `MapSystemProvider`。
2. 编队、技能槽位归 `BattleSetupProvider`。
3. 装备库存、材料、消耗品、记忆、穿戴关系归 `EquipmentInventoryProvider`。
4. 组织领地、建筑摆放、评级归 `OrganizationProvider`。
5. 页面组件可以有 UI 临时状态，但不能再存业务真相副本。

### 2.2 先改类型和配置入口，再改逻辑，再改页面

1. 改数据结构时，先看 `src/types/game.ts`、`src/types/battle.ts`、`src/types/organization.ts`。
2. 改可配置内容时，优先改 `src/config` / `src/data/config` / `src/data/battleSkills`，不要把数值直接塞进页面。
3. 页面只负责展示和交互，不负责发明新的业务规则。

### 2.3 不要绕开现有调用链做“近路修复”

1. 世界地图选择统一走 URL：`continent` / `dominion` / `region`。
2. 节点页、战斗页统一靠路由参数 `nodeId` 取上下文。
3. 英雄页页签统一走 `?tab=`。
4. 发现问题时，优先修入口函数或 Provider，不要在下游页面用补丁逻辑掩盖。

### 2.4 明确区分“正式闭环功能”和“占位页面”

当前代码里：

- 已接通闭环：世界地图地区切换、月结算、布告栏任务、英雄技能配置、装备穿戴、记忆穿戴、战斗、战斗掉落、任务进度回写、铁匠铺强化与打造、组织基地基础摆放。
- 明确占位：商铺大宗贸易、酒馆招募、仪式正式流程、组织功能建筑子页面。

做开发时不要误把占位页当成已有完整系统。

### 2.5 涉及英雄时先确认状态源

当前运行时英雄池由 `src/state/HeroRosterProvider.tsx` 管理，初始英雄由 `src/data/heroRoster.ts` 生成。

这意味着：

1. 运行时新增/删除英雄，不是简单页面改动。
2. 酒馆招募、正式英雄池、动态入队要优先改 `HeroRosterProvider`。
3. 如果只是调初始英雄生成规则，改 `src/data/heroRoster.ts` 和 `src/data/config/*`。

### 2.6 样式改动遵守现有命名分区

1. 全局样式集中在 `src/styles.css`。
2. 按模块前缀查找和新增 class：`map-`、`hero-`、`inventory-`、`battle-`、`team-`、`organization-`。
3. 不要为了临时修样式到处加无语义 class 或大段内联样式。

### 2.7 一次提交只解决一类问题

不要把下面几类内容混在一次开发里：

1. 功能改动
2. 大规模重构
3. 样式整体翻修
4. 配置结构迁移

## 3. 开发完成后必须验证

1. 主流程走通一次。
   - 地图类需求至少走一遍“世界地图 -> 节点 -> 功能页”。
   - 战斗类需求至少走一遍“节点 -> 战斗 -> 结算/复盘”。
   - 英雄/装备类需求至少验证“背包 -> 英雄页 -> 战斗适配”。
2. 页面无明显报错。
   - 控制台报错
   - 路由跳转
   - 关键按钮
3. 涉及数值改动时做针对性验证。
   - 地图数值：连续结算多个游戏月
   - 战斗数值：至少跑几场不同 archetype 的战斗
   - 任务数值：验证生成、推进、提交闭环

## 4. 文档更新要求

每次开发完成后，如果你觉得必要，做两件事：

1. 更新一个对应模块文档
   - 写清楚改动点、影响面、关键文件。
2. 新增开发记录
   - 路径：`docs/开发文档/开发记录/YYYY-MM-DD-任务名.md`
   - 模板：`docs/开发文档/开发记录/开发记录模板.md`

如果触发以下条件，还要补充：

1. 新增模块文档：更新 `docs/开发文档/README.md`
2. 新增可调参数：更新 `docs/开发文档/配置文件修改指南.md`
3. 新增页面 / 路由 / Provider / 核心目录：更新 `01-项目与目录总览.md`
4. 发现新的长期约定：更新 `AGENTS.md`
5. 发现临时实现 / 后续明确要补：更新 `TODO-项目后续开发.md`

## 5. 最低交付标准

1. 代码可运行。
2. 文档已同步。
3. 后续开发者只看文档就能定位主要改动文件。
4. 如果本次改动涉及跨模块链路，文档里必须写明入口和回写位置。
